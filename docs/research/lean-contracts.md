# Lean contracts and runtime boundaries: source investigation

Research ticket: [Investigate Lean contracts for proofs and runtime enforcement](https://github.com/Stoneguard-Games/LeanEiffel/issues/3); project map: [Chart LeanEiffel's Gobo and Lean contract integration](https://github.com/Stoneguard-Games/LeanEiffel/issues/1). Planning only; 2026-11-24. No prototype, repository changes, or product-semantic choice.

## Scope and inspected baseline

Lean-verifiable syntax replaces Eiffel contract syntax and is authoritative for preconditions, postconditions, and class invariants. Runtime DbC remains; supported obligations can be proved incrementally, while unproved obligations are explicitly reported and can execute with runtime checks. Contract placement remains open. This investigation concerns Lean's side of an existing-Gobo integration, not a replacement Eiffel compiler.

Source baseline: **Lean v4.36.0**, commit [611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9](https://github.com/leanprover/lean4/commit/611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9). GitHub's v4.36.0 commit endpoint resolved this SHA. Master was also identified as b8d19876fd6ac4219123dced4eaa29f43b87e2b9 during the investigation; findings below use the stable baseline and versioned manual. No Lean installation/build was performed. Version sensitivity matters: Decidable's current Bool-and-reflection representation arrived in [4.35](https://lean-lang.org/doc/reference/4.36.0/releases/v4.35.0/), so older descriptions of its constructors are not the implementation baseline.

## Source facts

1. **A proof is not an executable assertion.** Lean propositions inhabit Prop; their proofs are erased in compiled programs. Bool retains runtime data. A theorem being accepted establishes its elaborated formal statement relative to imported definitions and axioms; Lean does not establish that the statement expresses the intended program behavior. See [propositions](https://lean-lang.org/doc/reference/4.36.0/The-Type-System/Propositions/), [Booleans](https://lean-lang.org/doc/reference/4.36.0/Basic-Types/Booleans/), and [proof validation](https://lean-lang.org/doc/reference/4.36.0/ValidatingProofs/).

2. **Decidability is the bridge, where executable.** A computable Decidable (P s) supplies a Boolean with a proof connecting its outcome to P s. Source defines Decidable with decide : Bool and reflects_decide. This permits a proposition to drive runtime branching without keeping its proof at runtime. Classical.propDecidable uses choice and is explicitly noncomputable: classical decidability does not supply a runnable checker for arbitrary propositions. See [Prelude lines 1121-1174](https://github.com/leanprover/lean4/blob/611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9/src/Init/Prelude.lean#L1121-L1174), [Classical lines 80-84](https://github.com/leanprover/lean4/blob/611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9/src/Init/Classical.lean#L80-L84), and [decidability manual](https://lean-lang.org/doc/reference/4.36.0/Type-Classes/Basic-Classes/#decidable).

3. **Calling compiled Lean is possible; it is an ABI integration.** The documented C ABI supports exported definitions and external implementations, with Lean-specific data representations, initialization, and ownership rules. The manual calls this interface unstable and excludes compound C structs passed by value. The upstream reverse-FFI example exports a function; its C caller initializes the module, handles initialization failure, then invokes the export. This is a route for invoking an executable predicate, not invoking a theorem. See [FFI manual](https://lean-lang.org/doc/reference/4.36.0/Run-Time-Code/Foreign-Function-Interface/), [Lean export example](https://github.com/leanprover/lean4/blob/611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9/tests/lake/examples/reverse-ffi/lib/RFFI.lean), and [C caller](https://github.com/leanprover/lean4/blob/611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9/tests/lake/examples/reverse-ffi/main.c#L1-L29).

4. **Trust must be reported, not inferred from successful elaboration.** sorry expands to sorryAx; axioms can assert unproved statements. Audit dependencies transitively using #print axioms (or its tooling equivalent), distinguishing ordinary logical axioms, sorryAx, custom axioms, and native evaluation. native_decide compiles a closed decision computation and records its true result using a bespoke axiom; it extends trust to the compiler/runtime and runtime replacements rather than deriving that computation solely by kernel reduction. It does not prove a routine correct for arbitrary future inputs merely by checking one closed instance. See [sorry source](https://github.com/leanprover/lean4/blob/611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9/src/Init/Prelude.lean#L778-L794), [native evaluation source](https://github.com/leanprover/lean4/blob/611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9/src/Lean/Meta/Native.lean#L30-L87), [decide dispatch](https://github.com/leanprover/lean4/blob/611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9/src/Lean/Elab/Tactic/Decide.lean#L70-L99), and [validation manual](https://lean-lang.org/doc/reference/4.36.0/ValidatingProofs/). Unsafe definitions cannot participate directly in mathematical reasoning; external/runtime replacement equivalence is a further trust boundary ([recursive definitions](https://lean-lang.org/doc/reference/4.36.0/Definitions/Recursive-Definitions/)).

5. **Arithmetic types have concrete semantics.** Lean has arbitrary-precision Nat/Int and separate fixed-width integer types. Fixed-width operations can wrap: UInt32.add is defined over BitVec with an external runtime implementation. See [fixed-width manual](https://lean-lang.org/doc/reference/4.36.0/Basic-Types/Fixed-Precision-Integers/) and [UInt32.add source](https://github.com/leanprover/lean4/blob/611c117bfaf7b7ae1cfcf246ce6fba31e8f509e9/src/Init/Data/UInt/BasicAux.lean#L215-L235).

## Inferred obligations for LeanEiffel, not Lean or Gobo guarantees

There are two different claims to establish: (a) the runtime check implements the authoritative contract, and (b) the executed Eiffel routine satisfies that contract. A Lean model plus a proved theorem only establishes a model property until its connection to Gobo execution is justified. FFI does not supply this connection.

A candidate state relation must cover object identity, mutable fields, aliasing, null/void, dynamic types, and relevant heap reachability. Copies of selected field values can support pure snapshots; blindly treating an Eiffel object pointer as a Lean structure cannot. Frame conditions, permitted mutation, exceptional exits and calls into unmodeled code need assumptions or semantics. A proof about a pure getter needs a purity/stability justification if the Eiffel query can mutate, fail, or observe external state.

Postconditions need pre-state and post-state, arguments and Result. The translation must specify exactly what each old expression captures at routine entry, including references and later mutation; a general deep-copy interpretation must not be silently substituted. Inherited contracts need correspondence to Gobo's effective contracts, renaming/redefinition, dispatch, and invariant check boundaries. Establish these against Gobo/Eiffel primary sources in the companion investigation; this note does not assert their exact rules.

Numeric obligations must match Gobo's actual target widths, signedness, conversions, division, overflow and exception behavior. A proof using mathematical Int does not by itself prove a machine-integer update; possible approaches include fixed-width modeling or mathematical modeling plus proved range conditions.

## Feasible research paths, without selection

- **Compile executable Lean contract predicates; invoke through a Gobo/C bridge.** One authoritative contract elaborates to executable checking and proof propositions. Research snapshot extraction, ABI overhead, lifetime handling and checker-to-state correspondence; routine correctness still needs justified verification-condition generation or refinement.
- **Lower a supported shared contract core to Lean and Gobo runtime expressions.** This can retain Gobo's assertion machinery and avoid per-check Lean FFI. Both lowerings need a documented shared meaning and equivalence evidence; no separately authored Eiffel contract source is required.
- **Model a selected Gobo semantic/IR slice in Lean and establish refinement.** More work, but a path toward stronger assurance about executed bodies. Unsupported Eiffel features can remain explicitly outside static coverage while retaining their executable contracts. This grows proof coverage without inventing a smaller Eiffel compiler.

Runtime fallback requires an executable checker. An arbitrary noncomputable Prop is not made executable merely by labeling it unproved. The language must eventually choose how accepted authoritative contracts obtain runtime meaning: restrict a supported executable core, require a suitable decision procedure, or provide a checker plus justified reflection. This investigation leaves that product decision open.

Next experiments to specify, not implement now: (1) a finite arithmetic contract with its executable decision procedure and reflection proof; (2) positive/negative runtime boundary cases through an exported Lean checker and through generated Gobo assertions; (3) one mutable aliased object with old/Result and inherited effective contracts; (4) overflow, division and conversion cases against actual Gobo output; (5) an evidence report showing proved, unproved, unsupported, and axiom/native-dependent results separately. Include a deliberately false model-to-execution mapping to verify that the report does not overclaim. Pin source, compiler options, contract/VC identity and proof dependencies so later code changes invalidate stale evidence.
